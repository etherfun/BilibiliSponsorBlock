# 其他 AI 生成内容检测方式：调研与选型

本文回答一个问题：**除了第一阶段已落地的文本启发式规则，还有哪些路可走，值不值得在浏览器扩展里走。**

选型约束（来自本项目现状）：

- 运行在 B 站页面里的 content script，要**离线、低延迟、低内存**，不能阻塞滚动。
- 扩展已上架 Chrome / Edge / Firefox / Safari，**包体积与商店审核**都敏感。
- 不引入联网或第三方 API 作为默认路径（隐私 + 稳定性 + 账号风险）。
- 用户群体是普通观众，**误伤真人评论的代价远高于漏掉 AI 评论**（宁可少判，不可错杀）。

---

## 1. 文本启发式规则

### 1.1 可用的信号

| 信号 | 实现难度 | 运行成本 | 效果（本地实测） |
|---|---|---|---|
| 关键词/短语命中 | 极低 | 极低 | 对固定人设话术有效，对改写无效；**不可单独使用** |
| 句长分布（CV） | 低 | 极低 | 弱，真人规范长评同样低 CV |
| 标点使用（种类/熵） | 低 | 极低 | 弱，易受排版习惯影响 |
| 文本重复度（n-gram 新鲜度） | 低 | 低 | 中，对模板化文本有效 |
| 跨评论相似度（Jaccard） | 低 | O(n²)，需限长 | **强**，本次主力信号 |
| 重复家族聚类（并查集） | 低 | O(n²) 但常数小 | **强**，误报极低 |
| 文本长度/信息密度 | 低 | 极低 | 中，需与其他特征联合 |

### 1.2 结论

- **实现难度：低**。纯 TS，无依赖，已全部落地在 `src/content/aicg/`。
- **运行成本：可忽略**。一屏 20~40 条评论，构建一次上下文（含一次 O(n²) 但带长度预筛的并查集），实测单次扫描 < 5 ms 量级；重复扫描走 `WeakMap` 去重，不做重复计算。
- **误报率：可控但需设计**。实测标记侧 30/30 命中 AI、0 误伤；但**必须**把「单条结构特征」降权，并且要求跨评论证据才允许越阈值，否则规范长评会被误伤。
- **召回率：有上限**。改写型 AI（约 23% 的唯一文本 AI 评论）会被漏掉，见《aicg-comment-analysis.md》§4.4。

> 一句话：规则检测是**唯一能在第一阶段安全落地**的方案，但它擅长的是「批量/模板」，不擅长「单条高质量改写」。

## 2. NLP 与机器学习

### 2.1 专用 AI 文本检测分类器

现状（2026-11 检索）：

- **TMR / RoBERTa-base 类检测器**有 ONNX 版本可直接跑（`onnx-community/tmr-ai-text-detector-ONNX`），英文 RAID 榜单 AUROC 99.28%（含对抗样本）；作者开源的英文模型体积约 500 MB（fp32）级别，量化后仍在 100 MB+ 量级。
- 中文基准：**C-ReD**（arXiv 2604.11796）指出中文语料存在「模型多样性有限、同质化严重」问题；基于 CNKI 摘要 + DeepSeek R1/Phi4/Qwen2.5 生成数据的研究显示，RoBERTa 类模型对 Phi4 生成文本召回可达 100%，但对 **Qwen2.5 只有 88.91% 准确率**——越是「像人写的」模型越难判。
- 商业检测器（Copyleaks、Pangram）声称中文支持良好、准确率 99%+，但**只能通过 API 调用**。

评估：

| 维度 | 结论 |
|---|---|
| 模型体积 | 轻量中文可用方案最少 20~100 MB 量化，**对浏览器扩展偏大**（当前 content.js 已 2.7 MB） |
| 推理耗时 | 单条 50~200 ms（CPU/WASM），评论滚动时逐条跑不可接受 |
| 内存占用 | 100~300 MB 常驻，移动端浏览器会直接换出页面 |
| 中文能力 | **领域错配**：这些模型训练在论文/新闻/长文，对 60~100 字的 B 站评论、玩梗、emoji、颜文字泛化很差 |
| 浏览器可行性 | 技术上可行（onnxruntime-web / transformers.js），工程上代价大 |
| 是否需要联网 | 本地模型不需要；但模型下载本身要联网，且需进商店包 |

**判断：暂时不值得引入。** 短评论 + 玩梗语料是这类检测器最弱的场景，投入产出比很差。

### 2.2 Embedding 相似度

- 轻量中文 embedding（如 `bge-small-zh` 量化后 ~25 MB，或 `text2vec-base` ~100 MB）可以把「改写过的同一套说辞」聚到一起，直接补上规则检测的最大短板（§4.4 的漏检）。
- 但在浏览器里逐条算 embedding 仍然要 WASM 推理，成本与 2.1 同量级；**除非上服务端**。

**判断：第二阶段值得尝试，但优先「服务端/可选开关」而不是默认本地跑。**

### 2.3 小型文本分类模型

- 自己训练一个 2~8 MB 的轻量中文分类器（字符级 CNN / 蒸馏小 BERT）在理论上可行，且能针对 B 站评论语料微调，效果可能远好于通用检测器。
- 需要：**标注数据**（本项目目前零标注）、训练管线、持续迭代、误报监控。
- 现有可借鉴的社区实践（`dafeiyu-cleaner` 系列扩展）走的正是「离线规则优先 + 可选 LLM 精判」的混合路线，而不是本地分类模型——这本身是一个信号：**本地小模型的性价比还没被验证**。

**判断：第二阶段值得尝试（若有标注数据），当前不建议。**

### 2.4 可在线运行的 ONNX

技术路径已成熟（`onnxruntime-web` + WASM/WebGPU）。真正的瓶颈不是「能不能跑」，而是**模型体积与中文短文本效果**。若要试，建议：

- 只在用户主动点「复核这条」时按需加载模型（不随包分发），
- 用 `Web Worker` 避免阻塞主线程，
- 明确的「这是实验功能」提示。

## 3. 统计与语言学特征

| 指标 | 理论价值 | 实测/现实 | 结论 |
|---|---|---|---|
| **Perplexity（困惑度）** | 高：AI 文本通常困惑度更低、更「可预测」 | 需要与检测模型同源的语言模型；用错 LM 直接失效。中文短评论上下文太少，困惑度估计方差极大 | 理论可行，实际不可靠 |
| **Burstiness（复杂度变化）** | 高：人类写作句子复杂度波动大 | 与 F5（句长 CV）同源。60 字评论只有 2~3 句，统计量不足；实测真人规范长评也会低 | 只可作弱证据 |
| **Token 分布/重复模式** | 中 | 中文分词在浏览器里要做，且评论大量非规范写法；退化为字符 n-gram（本实现采用） | 已用轻量替代方案 |
| **句长分布** | 中 | 见上，弱证据 | 已降权使用 |
| **词汇多样性（TTR 等）** | 中低 | 短文本 TTR 方差极大，几乎不可用 | 不推荐 |
| **句法/语言模型特征** | 高 | 需要句法分析器，体积与延迟不可接受 | 不推荐 |

**重要提醒（写进结论）**：这些指标常被营销成「AI 检测器」，但在**短文本 + 中文 + 网络语**条件下，它们的独立判别力远低于宣传。本实现只把其中两项（句长均匀度、标点机械度）作为**加权弱证据**，并且有闸门防止它们单独越阈值。

## 4. 其他可利用的公开信息

| 信息 | 可用性 | 价值 | 备注 |
|---|---|---|---|
| 评论发布时间与时间分布 | 接口直接给 `ctime` | **高**：同账号连发间隔 < 20s 是铁证 | 需按作者聚合，第二阶段 |
| 同一用户多条评论 | 需按 `mid` 聚合或拉作者空间 | **高**：229 条同一模板 | 第二阶段（一次翻页即可聚合当前屏） |
| 多条评论文本相似度 | 前端已有 | **高**（已实现 F1/F2/F3） | 一阶段 |
| 评论与视频内容语义关联 | 需标题/字幕/摘要 | 中高：机械复述视频摘要 | 需 embedding，第二阶段 |
| 昵称/头像/简介特征 | 接口给 `member` | 中：`鱼/鲸/whale` 占比 37.6% | **谨慎**：昵称可伪装，且真人也会跟风改昵称玩梗；只能作为额外的弱信号，且默认关闭 |
| 账号等级 / IP 属地 / 设备指纹 | 接口部分可见 | **无关联** | **明确不采用**：与是否 AI 生成没有直接因果关系，且涉及敏感画像 |

**明确不用的东西**：账号等级、IP 属地、设备指纹、粉丝数、注册时间。这些既不能可靠指示 AI 生成，又会把「低等级新用户」整体打成可疑，属于歧视性误伤。

### 最终技术路线

**第一阶段（已实现，可直接落地）**

1. 规则检测内核（`src/content/aicg/detector.ts`）：模板复用 + 跨评论相似 + 重复家族为主，其余降权。
2. 决策层（`decision.ts`）与执行层（`executor.ts`）分离，检测器不碰 DOM。
3. 强闸门：跨评论证据不足时，置信度被压到阈值以下——**保证规范长评不被误伤**。
4. 跳过短评论与口语化评论。
5. 设置默认「禁用」，升级不影响现有用户。

**第二阶段（值得尝试，按收益排序）**

1. **同作者聚合信号**（F9）：当前屏按作者聚合，检测「同账号短时间连发同模板」。纯前端、无模型、收益高。
2. **评论流元数据**：接入 `mid` + `ctime`，做「同账号多评论相似度」。需要多拉几页，注意请求节流。
3. **可选语义复核**：在 `AicgDetector` 接口后接一个 `SemanticAicgDetector`，默认关闭；可用本地 embedding 或（用户自备 key 的）LLM 精判，只对「规则判定为边界」的评论调用。
4. **标注数据积累**：用「显示命中特征」+ 用户反馈（可加「这不是 AI」按钮）沉淀标注集，再决定是否训小模型。

**暂不值得引入**

- 通用英文/长文 ONNX 检测器（体积大、领域错配）。
- Perplexity / Burstiness 作为主判据（需要本地 LM，短文本统计量不足）。
- 账号等级、IP、设备指纹类画像（无因果关联，且伦理上不该做）。
- 默认联网调用第三方 API（隐私、稳定性、依赖风险）。

### 已预留的扩展点

`src/content/aicg/types.ts` 中的 `AicgDetector` 接口就是为此准备的：

```ts
export interface AicgDetector {
    detect(input: AicgCommentInput): AicgDetectionResult;
}
```

`AicgCommentInput` 已包含 `peers`、`sameAuthorPeers` 等上下文字段，后续接 embedding / 小模型 / 服务端精判时，**决策层与执行层不需要改动**，只需替换检测器实现并在设置里加一个开关。
